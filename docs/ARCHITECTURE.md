# Architecture notes

## Routes
| Route | Purpose | Indexing rule |
|---|---|---|
| `/` | Homepage — Hero, Latest Government Updates (tabs), Upcoming Government Exams, state/department/qualification directories | index |
| `/jobs` | All open jobs (URL-driven filters incl. `?organization=`) | index only without query params |
| `/jobs/[slug]` | Job detail — includes a "Related information" section: recruitment, exam hub, linked admit card/answer key/result, organization, state, qualification | noindex if demo or closed |
| `/central-jobs` | Central-level jobs | index if ≥1 open job |
| `/state`, `/state/[slug]/jobs` | State directory / landing | landing indexed only if ≥1 open job |
| `/department`, `/department/[slug]` | Department directory / landing | same |
| `/qualification`, `/qualification/[slug]` | Qualification directory / landing | same |
| `/recruitment/[slug]` | Recruitment cycle detail — linked jobs, admit card/answer key/result, exam schedule | index once published |
| `/exams`, `/exams/[slug]` | Exam hubs (overview, eligibility, syllabus, pattern, cut-off, previous papers, links back to jobs/admit card/answer key/result) | demo hubs and drafts noindex |
| `/admit-card` `/results` `/answer-key` `/exam-calendar` | Discovery sections (URL-driven filters) | index only without query params |
| `/admit-card/[slug]` `/results/[slug]` `/answer-key/[slug]` | Content detail pages | index once published |
| `/search` | Site-wide search across Jobs, Recruitments, Exams, Admit Cards, Results, Answer Keys, Organizations, each result labelled `[TYPE]` | always noindex (query-driven) |
| `/preparation` | Preparation hub | index |
| `/about /contact /advertise /disclaimer /privacy-policy /terms /editorial-policy /correction-policy` | Static/trust pages | index |
| `/login /register /alerts` | Account/alerts previews | noindex |
| `/admin/*` | Staff console (see "Admin" below) | noindex, requires a staff session |
| `/admin/[ref]/[id]/preview` | Signed, expiring staff-only draft preview (recruitment/exam/admit card/result/answer key/exam calendar) — same public view minus JSON-LD | noindex, 404 without a valid token |
| `/admin/sources`, `/admin/sources/[id]`, `/admin/review`, `/admin/review/[id]`, `/admin/ingestion`, `/admin/health`, `/admin/import`, `/admin/organizations(/new,/[id])` | Phase 3 content operations (see `docs/CONTENT_OPERATIONS.md`) | noindex, staff only |
| `/api/cron/sources`, `/api/cron/links` | Scheduled source checks / link monitoring (`CRON_SECRET`) | not pages |
| `/sitemap.xml /robots.txt` | Generated | only pages with real, published content are listed — never drafts, `/search`, or `/admin/*` |

Deviation from the brief's examples: department pages live at `/department/[slug]` (not `/jobs/up-police`) so job slugs and
department slugs never collide in the `/jobs/*` namespace. Exam Calendar entries have no own detail page by design — each
row links out to its Exam hub (`/exams/[slug]`) for full detail, so a schedule is never duplicated across two URLs.
Planned: `/state/[slug]/[district]/jobs` for districts, only when a district has content.

## Trust & SEO rules encoded in code
- No countdown or urgency badge without an officially recorded last date (`deadlineStatus`).
- `JobPosting` JSON-LD only for live, open, non-demo jobs with an official apply URL, source link, title, organisation and summary (never draft/review/expired/archived).
- Empty landing pages are `noindex` and left out of the sitemap.
- Search/filter/pagination variants are `noindex` with canonical to the clean URL; `/search` is always `noindex` (see below).
- Publishing requires source name, source-checked timestamp, notification or website URL, state and a qualification (enforced by DB trigger); every Phase 2B content
  type (Recruitments, Exams, Admit Cards, Results, Answer Keys, Exam Calendar) enforces the same official-source rule via its own `assert_publishable_*` function.
- Official links are visually separated (dashed box, external icon) and opened with `rel="noopener noreferrer"`.
- **Official vs Expected dates** (Phase 2B): every date field on Recruitments/Jobs/Exams/Admit Cards/Results/Answer Keys/Exam Calendar is really three columns —
  `<name>`, `<name>_status` (`official` | `expected` | null) and `<name>_text` (free-text wording, only for `expected`) — generated by the `add_date_status(table, col)`
  Postgres helper, with CHECK constraints so an `official` row always has an exact date and an `expected` row never claims one. `DateValue`/`dateLabel`
  (`components/gov/DateValue.tsx`) and `describeStatusDate`/`statusDateLabel` (`lib/date-display.ts`, server-safe) are the **only** place a date is rendered:
  official → exact date; expected → an "Expected" badge plus wording/month-year, never a specific day; neither set → "To be announced". No other component
  formats one of these dates directly.

## Data layer (Phase 3.6)

```
UI (src/app public pages, src/components)                 — imports only the facades below; never @supabase/*, never an implementation
  ↓
Application services / facades (src/lib/data/*.ts)        — index.ts (jobs), gov.ts, gov-items.ts, gov-exams.ts, gov-calendar.ts, ref.ts,
                                                             search.ts, exam-hub.ts, official-updates.ts: caching, ordering, paging,
                                                             search fan-out, labelling — written ONCE for both data sources
  ↓
ContentPort (src/lib/data/ports.ts)                       — the contract: RecruitmentPort · GovItemsPort · ExamPort · CalendarPort ·
                                                             RefPort · UpdatesPort + jobs: Repository
  ↓ chosen ONLY in src/lib/data/port.ts by DATA_SOURCE
demo/port.ts (in-memory synthetic)   |   supabase/port.ts (supabase-js → PostgREST, anon client, RLS decides visibility)
```

Shared rules live beside the ports, not inside an implementation: `statuses.ts` (LIVE vs VISIBLE statuses), `calendar-rules.ts`,
`query.ts` (open/closed, filters), `ref-model.ts`. Implementations contain data access and mapping only.

Enforced by tests:
- `tests/architecture.test.ts` — public UI imports no Supabase module and no implementation; only `port.ts` chooses; implementations never import facades;
  every data module is `server-only`; the service-role key is read in one server-only module.
- `tests/data-contract.test.ts` — the SAME contract checks run on `demoPort` and on `supabasePort` (against local PostgreSQL through the local API
  stand-in): statuses, demo flags, empty sitemaps for demo data, unknown slugs → null, and the full lifecycle (draft/review/unpublished/archived never
  open or list; expired opens but never lists).

Staff-only reads (draft previews through the staff member's own RLS session) are Supabase-only by nature and live in `staff-preview.ts`; admin pages
and the ingestion pipeline talk to Supabase directly (they need authentication, which demo mode does not have). Both run locally against the same
stand-in, so every path has a local implementation to test against.

**What cannot be tested until a real Supabase project exists:** real GoTrue/PostgREST behaviour, Supabase's own roles and default privileges, latency —
see `docs/SUPABASE_SETUP.md`. Supabase implementation prepared; local PostgreSQL/RLS tests pass; real Supabase validation pending.

### Generic content engine (recruitments, exams, admit cards, results, answer keys, exam calendar)
These six content types share one admin implementation: `src/lib/admin/content-config.ts` declares, per type, its table, route, form fields/sections and the
"ready to publish" checklist; `ContentForm`/`ContentList`/`ContentWorkflowPanel` and the generic `content-actions.ts` (save/transition/delete) are the only
code that renders or mutates any of them — adding a seventh type is a config entry, not a new page/component/action. Draft preview for a `previewable` type
goes through `/admin/[ref]/[id]/preview` with an HMAC-signed, 30-minute token bound to the record and the staff member (`lib/auth/preview-token.ts`), rendering
the exact public view component minus JSON-LD.

### Site-wide search
`/search` (`lib/data/search.ts`) fans one query out across Jobs, Recruitments, Exams, Admit Cards, Results, Answer Keys and Organizations in parallel, each
capped to a few results and labelled by type (`[JOB]`, `[ADMIT CARD]`, …). It is plain substring matching on titles/names via the same repository/list functions
the ordinary list pages use (so it can never surface a draft) — not AI search, which the brief explicitly excludes from this phase. `/search` itself, and every
result it can return, is always `noindex`; only the canonical detail pages it links to are indexable.

## Security model
Defence in depth, in this order of authority:
1. **Database (authoritative):** RLS on every table; permissions come from `role_permissions`/`has_permission()`; status changes are validated by the `jobs_before_write`
   trigger against `workflow_transitions`; publishing requires official-source fields (`assert_job_publishable`); editing a live job needs `job:publish` and flips it to *updated*;
   only super admins can touch super-admin rows and the last active super admin cannot be removed (`admin_users_guard`); every change is written to `audit_logs` by trigger with
   `auth.uid()` (or `system:*` for cron) and a before/after diff; internal notes live in staff-only `job_internal`; URL columns have `http(s)` CHECK constraints.
2. **Server (Next.js):** every admin page/layout/action calls `requireStaff`/`assertPermission` (`auth.getUser()` validated against Supabase Auth, then the caller's own `admin_users` row).
   Actions validate all input with zod and map database errors to safe messages. Editorial text is plain text rendered through React (no raw HTML), control characters are stripped.
3. **UI:** role-aware menus/buttons are convenience only.
`proxy.ts` refreshes the session cookie (HttpOnly, SameSite=Lax, Secure in production) and does an optimistic redirect; it is not a boundary. The **service-role key** exists only in
`src/lib/supabase/admin.ts` (`server-only`), used by the cron route and the create-admin script.

## Jobs workflow
`draft → review → published ⇄ updated → expired → archived` (see `workflow` in `permissions.ts`, mirrored in `workflow_transitions`). Editing goes through the atomic `save_job` RPC;
status changes through `transition_job` (both SECURITY INVOKER so RLS and triggers apply to the caller). Expiry: `expire_overdue_jobs()` (SECURITY DEFINER, callable by the service role,
DB sessions, or staff with `job:expire`).

## Admin
Routes: `/admin/login`, and behind `admin/(console)/layout.tsx` (staff required): `dashboard`, `jobs`, `jobs/new`, `jobs/[id]`, `recruitments`, `exams`,
`admit-cards`, `results`, `answer-keys`, `exam-calendar` (all six generic content types via `[ref]/[id]`), `audit`, `users` (read-only). Sidebar entries for
anything not yet built (organizations/departments/states/districts/qualifications management, alerts, settings) are still shown disabled as "Soon".

The dashboard (`admin/(console)/page.tsx`) reads one RPC, `admin_dashboard_stats()` (extended for Phase 2B in `0009_dashboard_stats_2b.sql`), and shows:
Jobs (published/draft/review/expiring-in-7-days/expired/needs-attention), a Recruitments/Exams live-count row, an Exam Calendar widget (upcoming/today/this
week — official dates only, an estimate is never "today"), an Admit Cards/Results/Answer Keys widget (live total + released in the last 7 days each), and a
Content Review widget (one count across Recruitments/Exams/Admit Cards/Results/Answer Keys/Exam Calendar rows in `review`, with a jump-link per type).

Ingestion (future): discovered → extracted → normalised → duplicate check → human review → published.
